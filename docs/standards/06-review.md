# 06 · 评审

> 提炼自 `code-review`（**MIT**，`arch3rPro/dsh-skills`）＋ 本仓库的实践。
> 核心：**沿两条轴分别评审，不要把两件事混成一句"看起来还行"。**

---

## 一、两条轴

| 轴 | 问什么 | 什么时候必看 |
|:--|:--|:--|
| **Standards**（规范） | 它**遵守本仓库的规范**吗？有没有明显味道？ | 总是 |
| **Spec**（意图） | 它**忠实实现了**原始需求/issue 吗？ | 总是 |

⚠️ **两条轴要分开报，并排给。** 混着说会导致：
"代码很干净"掩盖"功能没实现"，或"功能对了"掩盖"引入了技术债"。

**优先级**（`code-review` 原话）：**correctness、lifecycle、security 高于 style。**

---

## 二、`[人]` 本仓库特有的评审重点

### 1. ⭐ 先问「这次改动**该**有什么证据」，再看「有没有」

**这是本仓库最容易漏、也最值钱的一条。**
看一个 UI 改动时，第一句不是"代码写得对不对"，而是：

> **"这个改动，逻辑测试能看见吗？"**

看不见 ⇒ **必须有真机或真浏览器证据**。
⚠️ 本仓库连着三个 UI bug 都是"代码没问题 + 测试全绿 + 真机不对"。

### 2. ⭐ 检查**新断言的三个方向**

不要只看"断言写了没"，要看**它验过没**：

- [ ] 正向：把正确实现改错 → 它会红吗？
- [ ] 反向：构造"错的但像对的" → 它不会误绿吗？
- [ ] 第四向：构造"新功能落地"的样子 → 它仍然绿吗？

⚠️ **"加了断言"不等于"加了保护"** —— 空转的守卫**比没有更坏**。

### 3. ⚠️ 检查判据的**度量方式**

| 看到 | 判断 |
|:--|:--|
| 字符距离窗口（"±N 字符内"） | 🔴 **要求改成"追值来源"**（见 [03-assertions.md](03-assertions.md) §一） |
| 关键词存在性 | 🟡 小心"输入/输出混淆"和"别处残留" |
| 负判据（"禁止 XXX"） | 🔴 **要求配对正向要求**，否则会退化成"永远为真" |
| 钉了**实现方式**（"必须用 absolute"） | 🔴 **要求改成钉不变量** |

### 4. ⚠️ 检查"不许虚报"

看提交信息 / 报告里**有没有"我没验证的"一节**。
- 没有 ⇒ **问**："哪些部分你没验？"
- 有 ⇒ **看它诚不诚实**（有没有把"推演"写成"实测"）

### 5. 检查**共享工作区**的影响

- 改了 `test/` 下的**共享工具**吗？⇒ 必须跑全套
- 改了**宿主侧**吗？⇒ 提交信息里写了"要重启"吗？
- 用了 `git add -A` 吗？⇒ **禁止**（会带走别人未提交的改动）

## 三、`[清单]` 评审清单

### 正确性
- [ ] 它真的解决了原始问题吗？（读**需求**，不是读**代码**）
- [ ] 边界值 / 空 / 失败路径处理了吗？
- [ ] 有没有把"我们自己的错"报成"别人的错"？

### 生命周期
- [ ] 每个副作用有清理吗？
- [ ] 清理本身失败会怎样？

### 安全
- [ ] 路径范围限制住了吗？（`test/scope-guards.test.mjs`）
- [ ] 外部输入校验了吗？

### 规范
- [ ] `npm run check` 过了吗？
- [ ] 棘轮基线**没被手工编辑**吧？
- [ ] 新断言**指向规范条款**吗？没有的话**规范补了吗**？

### 证据
- [ ] 按 [02-evidence.md](02-evidence.md) 选了**最小集**吗？跑了吗？
- [ ] UI 可见改动 → 有真机/真浏览器证据吗？
- [ ] 新断言三个方向都验了吗？
- [ ] 报告里有"**我没验证的**"一节吗？

### 提交
- [ ] 提交信息说清**为什么**了吗？
- [ ] 是**独立的一笔**吗（没有夹带无关改动）？
- [ ] 用了 `git add -A` 吗？（**禁止**）

## 四、`[人]` 评审时**不该**做的

| 别做 | 为什么 |
|:--|:--|
| **只报 style 问题** | correctness / lifecycle / security 优先 |
| **说"看起来没问题"** | 那是**没评审**。要么给具体依据，要么说"我看了 X 部分，Y 部分没看" |
| **要求"把判据写得更细"来消掉假警报** | 假警报通常说明**度量方式错了**，不是参数错了 |
| **为了过测试而建议改实现** | ⚠️ 先问：**这条判据钉的是不变量还是实现？** |
| **默认"测试全绿 = 没问题"** | 见 §二.1 |

## 五、单人开发时怎么用这篇

本仓库主要是**一个人 + AI 协作**。所以：

- **自己改的东西也要过一遍这个清单** —— 尤其是 §二 那五条；
- **AI 写的代码要重点看 §二.1 和 §二.4**（这两条是 AI 最容易糊弄过去的）；
- **别省"三个方向"那一步** —— 本仓库实测：
  **7 次"判据不严"里 6 次是靠反向 bite-test 才发现的**，靠读代码读不出来。
