# 08 · Definition of Done

> **"做完了"的定义。** 逐条过，别跳。
> 最后一条（§九）是本仓库**最值钱、也最容易违反**的一条。

---

## 一、`[机器]` 机器已经替你验了的

| 项 | 命令 | 状态 |
|:--|:--|:--|
| lint 过（含棘轮基线） | `npm run lint` | 会拦住你 |
| 全部测试过 | `npm run test:unit` | 会拦住你 |
| 重复代码没增加 | `npm run dup` | 会拦住你 |

⇒ **这三条不用你操心，跑 `npm run check` 就行。**

---

## 二、`[清单]` 必须你自己确认的

### 证据

- [ ] 按 [02-evidence.md](02-evidence.md) 选了**最小集**，且**真的跑了**
- [ ] 如果改的是 **UI 可见输出**（位置/层级/尺寸）：
      - [ ] 跑了 `npm run render:verify`
      - [ ] **或者**在真机上肉眼看过 —— 并**说清是哪种**
- [ ] 如果改了 **`test/` 下的共享工具**：**跑了全套**（它是别人的输入）
- [ ] 如果改了 **`lib/platform.js`** 或任何**宿主侧**代码：
      在提交信息里写明 **「要重启 DSH 才生效」**
      （`lib/client.js` 才热载；宿主侧不热载 —— 本仓库踩过）

### 守卫

- [ ] **每条新断言**都构造过"已知有病的版本"，确认**它会红**
- [ ] 构造过"**错的但像对的**"实现，确认**不会误绿**
- [ ] 如果新断言是**负判据**（"禁止 XXX"）：**配了正向要求**，
      否则它会退化成"永远为真"（什么都不做也算通过）
- [ ] 如果判据用了**字符距离窗口**（"±N 字符内出现某词"）：
      **停下来** —— 本仓库实测这是**最不可靠**的度量方式，一重构就失效。
      改用「**追值来源**」或「全文件能力存在性 + 调用点语义」

### 规范

- [ ] 如果引入了**新的行为要求**：规范里有对应条款吗？没有就**先补规范**
- [ ] 如果**放宽**了某条守卫/棘轮：提交信息里说了**为什么**，并给了**替代兜底**

---

## 三、`[人]` 只能靠判断的

- [ ] **这个改动，我用最小代价验的方式对吗？** 有没有更直接、更接近真实的证据？
- [ ] **我是不是在用一个看不见它的测试床，验一个它看不见的东西？**
      （本仓库三个 UI bug 都是这么来的）
- [ ] **这条判据在实现被合理重构后还成立吗？**（§8.3 第 3 类的成因）
- [ ] **这次有没有"我以为想清楚了但其实没有"的地方？** 有就**写下来**

---

## 四、提交前

- [ ] 提交信息说清**为什么**，不只是**做了什么**
- [ ] **共享工作区禁用 `git add -A` / `commit -a`** —— 用
      `git commit --only <你自己的写入范围>` 或显式 `git add <路径>`
      （本仓库踩过：`git add -A` 把队友未提交的改动一起带走了）
- [ ] 工作区干净（`git status` 没有意外的残留）

---

## 五、⚠️ 三个"看起来做完但其实没有"的形态

| 形态 | 症状 | 真相 |
|:--|:--|:--|
| **假绿** | 测试绿，但它**没走到**你改的分支 | 用例先被另一道闸门拦下了。**加一条"确实走到了"的断言** |
| **空转守卫** | 守卫绿，但它**抓不到已知有病的版本** | **"抓不到已知 bug 的守卫"比"没有守卫"更坏** —— 没有你会警惕，空转的让你以为安全 |
| **预处理坏了** | 一片绿，因为守卫**读的输入是错的** | 例：没剥注释 ⇒ 注释里的字样满足了判据。**输入预处理必须自己也被验** |

⇒ 这三条**都不是"写错了会红"**，而是**"错了照样绿"**。**这才是最危险的。**

## 六、`[机器]` 关于棘轮

`eslint-suppressions.json` 是**基线**，规矩是：

- ✅ **只许减**：修好一处，跑 `npx eslint . --prune-suppressions` 把它从基线里删掉
- ❌ **不许增**：新代码违规会被 lint 直接拦住（**这是设计**）
- ❌ **不许手工编辑基线文件来"让它过"** —— 那是绕过棘轮，
      等于把"只许减不许增"变成"随便增"

---

## 七、`[清单]` 文档类改动

- [ ] 如果改动让**别的文档变错**了，**同一次提交里改掉**（别留烂账）
- [ ] 如果是**规范**改动：同步 `AGENTS.md`（如果它引用了改动的部分）
- [ ] 新增文档时问一句：**这个事实应该住在这篇里，还是该链接过去？**
      （同一事实两处 = 必然漂移）

---

## 八、`[人]` 什么时候**不该**追求"做完"

有些东西**现在做不完是对的**：

- 依赖**只有人能提供的东西**（凭据、真机、一个决定）；
- 依赖**还没到的条件**（"等依琪拍板"）。

⇒ 这时候**正确做法不是硬凑一个"完成"**，而是：
**把没做的部分明确写出来**（见 §九），并说清**卡在哪、条件到了做什么**。

---

## 九、⭐⭐ 不许虚报

> **这是本仓库最重要的一条。** 也是它和大多数项目最不一样的地方。

**规则**：

1. **没验的，必须自己标出来。** 报告里要有「**我没验证的**」一节。
2. **区分「实测」和「推演」。** 不许把"按规范推出来的"写成"实测的"。
3. **区分「逻辑测试证据」和「真机/像素证据」。** 前者**不能**用来支持后者。
4. **不许说"真机验证通过"**，除非真的有人在真机上看过。
5. **测试全绿 ≠ 功能对了。** 说"测试全绿"时，别暗示"功能没问题"。

**为什么这条排在最后但最重要**：

本仓库的历史里，**"如实说没验"救过很多次**。反过来，
**"看起来验了其实没验"**（§五 那三个形态）造成的损失最大 ——
因为它**消耗的是信任**，而信任是**唯一不能靠工具补回来的东西**。

**具体做法**（照抄这个格式）：

```md
## 验证
- `npm test` → 30/30 全绿
- 端到端变异：把 `flex:none` 删掉 ⇒ 守卫红 ✅

## ⚠️ 没验证的
- 🔴 真机肉眼没看：面板里点缩略图开浮层、按一次 Esc 的手感 ——
  证据是假 React 的 DOM 树 + 真 Chrome 几何，**不是**真机像素
- ❌ 焦点在跨文档 iframe 里时收不到按键 —— 未实测
```
