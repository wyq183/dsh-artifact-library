# 07 · 提交

> 本仓库的提交信息**质量很高，是它的资产之一**。这篇把已有的风格固化，
> 并补上"共享工作区"那条硬教训。

---

## 一、格式

```
<type>(<scope>): <一句话说清做了什么>

<正文：为什么 + 怎么做的 + 证据 + 没验证的>
```

### `type`

| type | 用于 |
|:--|:--|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `test` | 只动测试/守卫 |
| `docs` | 只动文档 |
| `chore` | 基建、依赖、配置 |
| `refactor` | 不改行为的重构 |

### `scope`（可选但推荐）

用**模块名**：`client` / `store` / `tools` / `platform` / `settings` / `http` /
`overlay-escape` / `defersave` / `规范` …

### 一句话（主题行）

⚠️ **说"做了什么 + 后果"，不说"改了哪个文件"**。

| ❌ | ✅ |
|:--|:--|
| `fix: 修改 client.js` | `fix(client): 详情预览的视频控件被裁掉 —— 容器被 flex 压缩 + 视频缺 max-height` |
| `update platform.js` | `fix(platform): 「在文件夹中显示」窗口建了却不显示 —— spawnSoft 无条件 windowsHide: true` |
| `test: 加测试` | `test(overlay-escape): 禁飞区判据升级为「查可交互元素」+ 记下 40px 的证据来源` |

⭐ **本仓库的好传统**：主题行里**直接写出根因**。
这让 `git log --oneline` 本身就成为一份**可检索的教训库**。

## 二、正文的结构

**不是每笔都要长**，但**修 bug 的提交必须写清"为什么"**。参考结构：

```md
## 起因
（触发这件事的原话 / 现象 / 需求）

## 根因
（**为什么**会这样。要具体到机制，不是"代码写错了"）

## 修法
（怎么改的 + **为什么选这个改法**，以及被否掉的替代方案）

## 验证
（跑了什么、结果如何）

## ⚠️ 没验证的
（**必须有这一节**，没有就写"无"）
```

## 三、⭐⭐ 两条本仓库特有的硬规矩

### 1. **必须有「我没验证的」一节**

这是本仓库**最值钱的传统**。理由见 [08-dod.md](08-dod.md) §九。

写法（照抄）：

```md
## ⚠️ 没验证的
- 🔴 真机肉眼没看：面板里点缩略图开浮层的手感 ——
  证据是假 React 的 DOM 树 + 真 Chrome 几何，**不是**真机像素
- ❌ 焦点在跨文档 iframe 里时收不到按键 —— 未实测
```

⚠️ **区分「实测」和「推演」**，**不许把推演写成实测**。

### 2. **共享工作区禁用 `git add -A` / `commit -a`**

> ⚠️ **这条来自一次真实事故**（记在 `docs/SUBMIT-CHECKLIST.md`）：
> 当晚用 `git add -A` 提交文档时，**把队友尚未提交的 `lib/client.js` 改动一起带走了** ——
> 结果是 `git log -S <符号>` **只会命中一笔讲文档的提交**，
> **没有任何一笔说明"为什么会有那段代码"**。

**正确做法**：

```sh
git add <你自己的路径>                        # ✅ 显式列
git commit --only <你自己的写入范围>            # ✅ 更严
git add -A / git commit -a                    # ❌ 禁止
```

⚠️ **AI 协作时尤其危险** —— 多个 agent 共享同一个工作区，
`-A` 会把别人**正在写**的东西一起提交。

## 四、什么时候**该**拆成多笔

| 情况 | 怎么办 |
|:--|:--|
| 修 bug 的过程中"顺手"改了别处 | **拆两笔**（`fix:` + `chore:`） |
| 重构 + 新功能 | **拆两笔**（`refactor:` 先，`feat:` 后）—— 否则 diff 读不出来 |
| 改规范 + 按规范改代码 | **拆两笔**（`docs:` 先，`fix:` 后） |
| 一次改动同时动了**产品代码和它的守卫** | ⚠️ **可以一笔**（它们是一件事） |

⚠️ **"独立的一笔"的判据**：**这一笔单独 revert 掉，系统还自洽吗？**

## 五、`[机器]` 提交前的自动检查

```sh
npm run check     # lint + 全部测试 + 重复代码 + 棘轮
```

⚠️ **别用 `--no-verify` 跳过** —— 那是把"门禁"变回"自觉"。
真觉得某条门禁不对，**改门禁本身**（并说明为什么），别绕过它。

## 六、推送

- **远程**：`https://github.com/wyq183/dsh-artifact-library.git`
- ⚠️ **本机 GitHub 直连被墙** ⇒ 用镜像（`ghproxy.net` 之类），或让依琪授权

- 推送后**重新取**一遍状态再报告（见 [08-dod.md](08-dod.md) §九 和 §8.5 的"报前重取"）

## 七、`[清单]` 提交前逐条过

- [ ] 主题行说清了**做了什么 + 后果**（不是"改了哪个文件"）
- [ ] 修 bug 的提交写了**根因**（具体到机制）
- [ ] 有 **「我没验证的」** 一节
- [ ] 没验的部分**没有伪装成验过的**
- [ ] **没用 `git add -A`**
- [ ] `npm run check` 过了
- [ ] 工作区**没有意外的残留**（`git status`）
- [ ] 这一笔**单独 revert 掉还自洽**
