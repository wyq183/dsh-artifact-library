# 01 · 变更流程

> 从「想做点什么」到「提交」，七步。**不是仪式 —— 每一步都对应一个踩过的坑。**

---

## 全景

```
① 定位     这次改动属于哪一类？          → 决定后面全部
② 先定规范  要加新断言？先补规范条款       → 否则断言在"保护 bug"
③ 实现     写代码
④ 选证据   按 02-evidence 选最小集         → 别无脑跑全套
⑤ 守卫验收  拿"已知有病的版本"验每条新断言  → ★ 最容易省、最不能省的一步
⑥ DoD 自检  按 08-dod 逐条过               → 特别是"不许虚报"
⑦ 提交     按 07-commit 写信息             → 说清"为什么"，不只是"做了什么"
```

---

## ① 定位：这次改动是哪一类？

**先分类，再动手。** 因为**不同类别的"验"完全不是一回事**：

| 类别 | 典型 | 关键问题 |
|:--|:--|:--|
| **纯逻辑** | 一个纯函数、一个算法 | 契约清楚吗？边界值列了吗？ |
| **UI 可见输出** | 布局、尺寸、位置、层级 | ⚠️ **逻辑测试看不见** —— 见 [02-evidence §三](02-evidence.md) |
| **落盘 / 持久化** | 写文件、撤销凭据 | **失败路径**测了吗？（成功路径是容易的那半） |
| **跨平台** | 路径、进程、编码 | Windows 和 Linux 的差异点在哪？ |
| **安全边界** | 路径范围、CSRF、注入 | 攻击者会怎么绕？ |
| **接口 / 契约** | HTTP 端点、工具 schema | 形状冻结了吗？谁在消费？ |
| **文档 / 规范** | 本目录 | 改了它，**有没有代码要跟着改**？ |

⭐ **如果一条改动同时属于两类，按"更危险"的那类走。**
例：改 `lib/client.js` 的 CSS —— 既是"纯逻辑"（CSS 字符串拼对了）又是"UI 输出"
（渲染出来对不对）。**按后者走。**

---

## ② 先定规范：要加新断言？先补规范条款

> 来自 `ARCHITECTURE.md` §8.3 第 1 条：
> **「断言必须指向规范条款。实现变了断言就成了『保护 bug』。
> 需要新断言时**先补规范**（如 UI-SPEC §十一），再照钉。」**

**什么意思**：断言是**规范的执行者**，不是**实现快照**。
如果你要钉的行为**在任何规范里都没写**，那你钉的到底是"应该的"还是"现在的"？

⇒ 顺序永远是：**规范 → 断言 → 实现**（或至少 规范 → 实现 → 断言，但规范要在前）。

⚠️ **反例**（本仓库真实发生过）：`H15` / `K13` 两条守卫断言的是 `ok === false`，
也就是**把当时那个 bug 的行为钉成了期望**。修 bug 时它们立刻红了 ——
**守卫在替 bug 站岗**。正解是**保留意图、换掉形状**，不是删掉它。

---

## ③ 实现

没有额外规矩，除了 [05-code.md](05-code.md) 那几条。

⚠️ **一条**：如果你发现**改着改着范围变大了**（"顺手"改了别处），
**停下来** —— 要么拆成两次提交，要么在提交信息里明说。
本仓库踩过：`git add -A` 把队友未提交的改动一起带走了。

---

## ④ 选证据：按 [02-evidence.md](02-evidence.md) 选**最小集**

核心原则（来自 `minimal-evidence-checks`）：

> **match the evidence to the surface.**
> 每个行为改动都需要**最窄的、能因它回归而失败**的那个检查 —— 不多不少。
> **不要仅仅因为"接下来要提交了"就重跑一个已经绿了的检查。**

---

## ⑤ ⭐ 守卫验收：每条新断言都要拿"已知有病的版本"跑一遍

**这一步最容易省，最不能省。** 本仓库的纪律（`ARCHITECTURE.md` §8.3 第 6 条）：

> **每条断言写完，先构造一个「错的但像对的」实现跑一遍 —— 不是可选步骤。**

**三个方向**（**三个都要做**）：

| 方向 | 做法 | 能发现 |
|:--|:--|:--|
| **正向** | 把**正确实现**改错，看断言是否变红 | 判据**过窄**（漏报） |
| **反向** | 构造**「错的但像对的」实现**，看断言是否误绿 | 判据**过宽**（误放行） |
| **第四向** ⭐ | 构造**「新功能落地」**的样子，看断言**是否仍然绿** | 判据会不会**在别人做对事时报警** |

⭐ **一条实用判据**（原话）：
> 写断言时问自己 —— **「如果我是一个想偷懒的实现者，
> 怎么用最少的改动让它变绿，而功能其实是假的？」** 然后**真的那么改一次**。

⚠️ **三个方向的完整做法、判据度量方式的可靠性排序、以及"什么时候不该写判据"** ——
**在 [03-assertions.md](03-assertions.md)**（那是本仓库最值钱的一篇）。
完整论证与全部反例 → `ARCHITECTURE.md` §8.3 / §8.4。

---

## ⑥ DoD 自检

按 [08-dod.md](08-dod.md) 逐条过。**特别是最后那条"不许虚报"。**

---

## ⑦ 提交

按 [07-commit.md](07-commit.md)。要点：
- **说清"为什么"**，不只是"做了什么"；
- **没验的部分要写进提交信息**（这是本仓库的传统，也是它最值钱的地方）；
- **共享工作区禁用 `git add -A`**。

---

## 附：什么时候该写 ADR / postmortem

| 触发 | 写 |
|:--|:--|
| 做了一个**会影响后来人**的设计决定（选型、契约、格式、流程） | [templates/adr.md](templates/adr.md) |
| 一个 bug **隐蔽、系统、重新发现代价高** | [templates/postmortem.md](templates/postmortem.md) |
| 一次"我以为想清楚了但错了" | 至少写进提交信息；反复出现就写 postmortem |

⚠️ **别为了写而写。** ADR 的门槛是"**后来人会问为什么**"；
postmortem 的门槛是"**这东西还会再犯**"。
