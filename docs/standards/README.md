## 30 秒版

```sh
npm test          # lint + 全部测试（提交前必须过）
npm run check     # 全门禁（= lint + 测试 + 重复代码）
```

**三条不能破的**：

1. **改了 UI 就必须真机看** —— 逻辑测试**在物理上看不见**布局（位置/层级/尺寸）。
   本仓库为此刻意建了 `npm run render:verify`（真 Chrome 量几何）。
2. **每条守卫都要拿"已知有病的版本"验过** —— 没验过的守卫是**安全感的假象**，
   比没有守卫更坏。
3. **不许把没验的说成验了** —— DoD 里明写这一条。报告里没做的部分必须自己标出来。

## 每条规范都标了「能不能机器强制」

这不是装饰 —— **它决定你该把力气花在哪**。

| 标记 | 意思 | 你能指望它 |
|:--|:--|:--|
| `[机器]` | 有工具/脚本会在你提交前**拦住**你 | 想违反也违反不了（除了 `--no-verify`） |
| `[清单]` | 有**明确的检查项**，但要人执行 | 漏了是你的责任，不是"不知道" |
| `[人]` | 只能靠判断，没有清单能覆盖 | 这条是**为什么需要人**，不是流程缺陷 |

⚠️ **本仓库的历史教训**：以前所有规矩都是 `[人]` 或纯文档，
结果**连着三个 UI bug 在"30 个测试文件全绿"的状态下上线**。
⇒ 新增规矩时，**先问能不能做成 `[机器]`**；做不成的，才降级成 `[清单]`。

⚠️ **并且：引用一条命令之前，先确认它真的存在。**
本目录第一次写出来时引用了 `npm run check` / `dup` / `render:verify`，
**三个都不存在** —— 而 §一 B3 早就警告过「**文档里的命令会被照着执行**」。
⇒ 现已补齐（见 `package.json`）。

## 改规范的规矩

规范本身也是代码，也要走流程：

1. **别处只链接到这里，不复制正文。** 复制必然漂移。
   ⚠️ 反向也成立：**本目录不复制 §8 的论证**，只链过去（见上面的分工）。
2. **改规范 = 改行为**。如果新规矩会让人改代码，**先在新规矩里写清迁移路径**
   （例：`max-lines` 用棘轮基线，老文件豁免、新文件受限）。
3. **能机器强制的，必须同时提交那个机器**。只写"应该 XXX" = 没写。
4. **不许悄悄放宽**。放宽一条守卫要在提交信息里说**为什么**，并给出替代的兜底。
5. **引用命令前先跑一遍它**（确认存在、确认名字对）。
6. **改了规矩要回头搜一遍**：仓库里有没有**别的文档在教相反的做法**？
   （实证：`SUBMIT-CHECKLIST` §一 B3 禁 `git add -A`，同一文件 §五 却在教 `git add -A` ——
   立了规矩**没回头清**，就是这种结果。）
7. 改完**同步 `AGENTS.md`**（如果它引用了改动的部分）。
