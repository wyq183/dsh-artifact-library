> 建立：2026-09-30 ｜ 触发原因：**真机首次启动就卡住了**，而这个插件要奔着官方插件市场去
> 状态：**根因排查中**，本文先如实列出「已暴露的」与「还没暴露但一定会遇到的」风险

## 一、已经真实暴露的问题（不是假设）

### 🐛 问题 1：真机首启 90 秒超时，且修复后**仍卡**

**现象**（2026-09-30 08:36 首次真实启动）：

| 观察项 | 结果 |
|:---|:---|
| `POST /files/start` | HTTP 500，耗时 90.6 秒，`Everything 实例启动后未在 90 秒内就绪` |
| Everything 进程 | **存在**（PID 56752，窗口标题正确） |
| `es -get-everything-version` | ✅ 退出码 0，返回 `1.5.0.1423`（**IPC 握手是通的**） |
| `es -get-result-count` / `-n 5 *` | ❌ **卡死不返回**（150 秒+） |
| Everything CPU | **0%（完全空闲）**，内存 47 MB |
| 库文件（`.db`） | **从未生成** |

**已排除的原因**（都做了对照实验）：

| 假设 | 实验 | 结论 |
|:---|:---|:---|
| ini 编码错误（UTF-8 vs GBK） | 对比 Everything 自己写的 ini；GBK 解码确实乱码 | ❌ **不是主因** —— 纯英文范围 + 同样 UTF-8 编码完全正常 |
| 中文路径 | 单独用 `中文测试` 目录做范围 | ❌ **不是** —— 中文目录 0.1 秒返回 2 行，索引正确 |
| 范围里有不存在的目录 | 13 个里有 2 个已删除 | 🟡 **已修**（过滤），但修完**仍然卡** |
| 库文件自引用（库在 `.dsh` 里） | 把库移到 `%LOCALAPPDATA%` | 🟡 **已修**，但修完**仍然卡** |
| 等待时间不够 | 90 秒 → 300 秒 | 🟡 已调，但**不是时间问题** —— CPU 全程 0%，根本没在扫描 |

**当前最强的两个待验证假设**：

1. **超长路径 / 特殊路径**：`.dsh` 下有大量 `node_modules\.pnpm\...` 深层嵌套，
   路径可能超过 Windows 260 字符上限 → Everything 在 folder 模式下可能卡住
2. **某个特定目录**导致：需要二分法逐个排除（`.dsh` 单独 → 正常/卡？→ 缩小到子目录）

> ⚠️ **诚实结论：根因尚未确定。** 在此之前**不能声称已经修好**。

## 二、抗风险能力评估（按「会不会崩」排序）

### 🔴 P0：会让插件**不可用**的风险

| # | 风险 | 现状 | 需要什么 |
|:--|:---|:---|:---|
| 1 | **索引范围过大**（几十万文件）→ 启动超时 | ❌ 只调了超时，没解决 | **不阻塞启动**：后台建索引 + 前端显示进度；或**限制范围规模**并在 UI 上提示 |
| 2 | **实例启动后不响应 IPC**（本次现象） | ❌ 无处理 | **启动健康检查要有超时兜底**：探测失败 → 明确报错 + 建议（缩小范围/查看日志），**不能挂死** |
| 3 | **超长路径 / 特殊字符路径** | ❌ 未验证 | 需实验确认；若确认，需在范围计算时**剔除或告警** |
| 4 | **杀毒软件拦截 `Everything.exe`** | ❌ 无处理 | 启动失败要能被识别（进程不存在 / 立即退出），给出**人话提示** |
| 5 | **用户已有同名实例 `DSHArtifacts`** | 🟡 设计上隔离，未测 | 启动前检测同名实例并给出提示 |
| 6 | **Everything 崩溃 / 被任务管理器杀掉** | ❌ 无处理 | 查询失败要能**自动重启实例**并重试一次 |

## 三、上官方市场前必须补齐的

按优先级：

1. **【阻塞】根因排查**：确定「实例不响应 IPC」到底是什么导致 —— 否则用户一装就崩
2. **【阻塞】启动不能挂死**：任何异常都要在有限时间内变成**一句人话 + 一个可操作建议**
3. **【阻塞】优雅降级**：Everything 不可用（被杀毒拦、被删、平台不符）时，
   **产物库原有功能完全不受影响**，只是「文件」视图显示不可用原因
4. **【重要】范围规模化处理**：给出上限策略（超限时提示/自动收窄），并在 UI 显示范围规模
5. **【重要】安装即测用例**（写进 README/上架材料）：
   - 空范围（没有任何产出）
   - 小范围（1 个目录）
   - 大范围（几十万文件）
   - 含已删除目录
   - 含中文路径
   - 用户已有 Everything 在跑
   - 无管理员权限

## 四、我打算怎么改（待你确认）

**架构层面的调整**（不是再打补丁）：

1. **启动永不阻塞请求**
   - `ensureReady` 立即返回「已开始启动」，真正的建索引进后台
   - 前端轮询 `status`（含 `resultCount`）显示进度
2. **健康检查与自愈**
   - 探测超时 → 判为「不健康」→ 自动尝试重启一次（走 `es -exit`，不强杀）
   - 仍失败 → 记录 `lastError` 并**停止重试**（不无限循环烧资源）
3. **范围守卫**
   - 启动前对每个范围目录：存在性 + 可达性 + 规模预检
   - 规模超阈值（如 20 万项）→ 在 UI 上警告并提供「收窄范围」入口
4. **隔离到底**
   - ini / 库 / 状态文件**全部**移出可能被索引的目录
5. **降级开关**
   - 设置项 `indexEnabled`（默认开）；关掉后一切回到 v0.6.0 行为，零残留
