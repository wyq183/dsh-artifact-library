# 架构说明 · 文件索引层

> 版本：v0.7.0 ｜ 建立：2026-09-30 ｜ 适用：DSH 0.2.0-rc.2（desktop profile）

---

## 一、为什么做这个

官方文件页 `@deepseek-ai/dsh-client-ui-sidebar-files` 的 README **自己写明了**两条限制：

> - **只有列目录。** 没有搜索、产物过滤、拖拽、重命名、右键菜单或当前文件高亮。
> - **只有一个根。** 树以会话工作目录为根；**Host 本来也拒绝工作区根之外的路径**。

也就是说官方能力 = **逐层网络拉取 + 无搜索 + 锁死工作区根**。

本项目补的正是这三块空白：

| 官方缺的 | 本项目补的 |
|:---|:---|
| 没有搜索 | **毫秒级**本地索引检索（Everything 引擎） |
| 锁死单个会话的工作区根 | **跨工作区 + 已登记产出目录**的统一视图 |
| 只有"文件" | 产物语义层：项目分类 / 星级 / 备注 / 引用 / 自动精炼 |

## 三、数据流（一次搜索）

1. 用户在「文件」视图输入，或模型调用 `search_files`
2. → `GET /ext/artifacts/files?q=…`（或工具内部直接调引擎）
3. → `http.js` 分发 → `engine.search()`
4. 引擎未就绪时先 `ensureReady()`：
   - 按当前范围**重写 ini**（只在内容变化时写；写盘后需重启实例才生效）
   - **探测**实例（`es -get-everything-version`，退出码 0 = 活着）
   - 没跑就**拉起**（detached，独立于宿主存活）→ 轮询等就绪（最多 90 秒）
   - ini 变了则**先正常关闭再启动**
5. `es.js` 执行 `es.exe -instance DSHArtifacts -export-json <临时文件> -utf8-bom …`
6. 读回文件、`JSON.parse`、**归一化**（FILETIME → Unix 秒；路径拆出 name/dir/ext）
7. 返回 `{ ok, rows, total, elapsedMs, status }`

## 四、关键设计决策（每条都有实测依据）

| 决策 | 为什么这么做 |
|:---|:---|
| **内置 Everything 便携版**（而非要求用户安装） | MIT 许可**实读 `LICENSE.txt` 确认**可分发；用户零安装；与用户已有实例完全隔离（各自 ini/db/进程/IPC） |
| **只索引「工作区 + 已登记产出目录」** | ① 隐私边界清晰 ② **免管理员权限** —— 官方明示 folder indexing「标准用户 + 便携版即可」，不依赖服务 |
| **走 `-export-json` 而不是读 stdout** | es.exe 的 stdout 是**系统 ANSI（GBK）**，Node 内置**不支持 GBK 解码** → 中文文件名必乱码。export 通道写文件是 UTF-8+BOM |
| **懒启动** | 不搜索就不启动任何进程 —— 零常驻开销，不打扰用户 |
| **正常退出（`es -exit`）而非强杀** | Everything **退出时才写 ini**；强杀会丢范围配置 → 下次按默认索引**全盘** = 隐私事故 |
| **串行查询队列** | Everything 本身很快；串行可避免临时文件撞名、避免打满磁盘 I/O |
| **`files` 路由排在 `GET :id` 之前** | 否则 `id='files'` 会被 `store.get()` 当成产物 id 处理 |
| **仅限本机回环** | 文件系统信息不外给局域网（非回环来源一律 403） |
| **引擎缺失返回 503 而非抛错** | 客户端 UI 已热载但宿主路由未加载是常见中间态，要能优雅降级 |

## 五、生命周期

```
应用启动
  └─ 插件 apply：创建引擎对象（**不启动任何进程**）
       └─ 注册路由 /ext/artifacts/files*、注册 search_files 工具

首次搜索 / 首次打开「文件」视图
  └─ ensureReady(scope)
       ├─ ensureIni(scope)   → 内容变化才写盘
       ├─ ping()             → 活着？
       ├─ 需要时 shutdown() → 先正常关（保证旧 ini 落盘）
       ├─ spawnInstance()   → detached + unref
       └─ waitReady(90s)    → 轮询 -get-result-count

日常
  └─ 每次搜索：确保就绪 → es 查询 → 归一化返回

应用退出
  └─ 引擎 effect 的 disposer → shutdown()（es -exit）
```

**范围变化**（新增工作区 / 新登记产出目录 / 用户加目录）：
下次 `ensureReady` 会重写 ini 并**重启实例** —— 旧库文件保留，Everything 会重建索引。

## 六、安全边界

| 边界 | 实现 |
|:---|:---|
| **不索引全盘** | ini：`auto_include_fixed_volumes=0` + 清空 `ntfs_volume_paths` + `folders=` 白名单<br>实测：限定前 3,217,522 条 / 118 MB → 限定后 **6 条 / 422 bytes** |
| **不需要管理员** | folder indexing 官方支持标准用户；ini 里 `run_as_admin=0` |
| **不碰用户的 Everything** | 独立实例名 `DSHArtifacts`；不修改/替换/卸载用户安装 |
| **不读文件内容** | Everything 只索引文件名与路径；本插件也不读正文 |
| **不外传** | 全部本地；无遥测、无网络请求 |
| **局域网隔离** | `/ext/artifacts/files*` 不在回环白名单 → 非本机来源 403 |
| **不改用户目录** | 所有运行时数据在插件数据目录与 `vendor/` 下的 ini/db |

## 七、已知限制（如实说明）

- **只搜文件名/路径，不搜内容** —— 按内容找文件请用 `grep`。这是 Everything 的设计，也是它快的原因。
  （内容检索是后续版本的事。）
- **首次启动索引需要数十秒** —— 首次拉起 Everything 并建立索引；之后毫秒级。
- **Windows only** —— Everything 是 Windows 工具。其他平台需要换引擎（未实现）。
- **包体 +5.26 MB** —— 内置的 Everything 便携版 + ES 命令行。
- **工作区收集是"尽力而为"** —— 官方 `follow()` 的返回形态未在文档中写死，本实现做多形态兼容；
  拿不到时只影响「工作区」那一路，不影响已登记产出目录。
- **范围是白名单快照** —— 新增目录需下次 `ensureReady` 才纳入（会自动重启实例）。

### 8.1 验收必须绑「已提交的 blob」，不是「工作区此刻的样子」

多人并行开发时工作区永远在动（实测：`lib/client.js` 十分钟内变过 5 次）。
此时拿工作区跑测试，**两次运行测的可能不是同一个版本**，绿灯就不可复现。

**正确做法**（经实跑验证）：

```powershell
# 1) 取出已提交的 blob（走 git 对象，不经过文件读写 → 规避 CRLF/编码差异）
node -e "const{execSync}=require('child_process');const fs=require('fs');fs.writeFileSync(process.env.TEMP+'/pinned-client.js',execSync('git cat-file blob HEAD:lib/client.js',{maxBuffer:2e9}))"

# 2) 这就是要写进交付说明的 pin（对 blob 求 sha256）
node -e "const{execSync}=require('child_process');console.log(require('crypto').createHash('sha256').update(execSync('git cat-file blob HEAD:lib/client.js',{maxBuffer:2e9})).digest('hex').slice(0,16))"

# 3) 用该副本复跑「客户端 3 套」（只有它们支持 argv[2] 传路径）
node test/ui-spec.test.mjs       "$env:TEMP\pinned-client.js"
node test/client-render.test.mjs "$env:TEMP\pinned-client.js"
node test/client-apply.test.mjs  "$env:TEMP\pinned-client.js"
```

> ⚠️ **边界（别写错）**：**只有客户端 3 套**（`ui-spec` / `client-render` / `client-apply`）
> 需要换成 blob 副本。另外 6 套（`icons` / `file-search-tool` / `http-files` /
> `scope-guards` / `workspace-watcher` / `session-changes`）测的是**宿主侧模块**
> （`lib/index/*`、`lib/http.js`、`lib/icons.js`），直接读各自文件、
> **不受 `lib/client.js` 改动影响** → **跑工作区即可**。

**pin 的两种哈希口径（都会遇到，必须标明是哪一种）**：

| 口径 | 怎么取 | 长什么样 |
|:---|:---|:---|
| **git 对象 id（SHA-1）** | `git rev-parse HEAD:lib/client.js` | `c5f025deca8f4501449101cedcef0434fb1548f0`（40 位）|
| **内容 sha256[:16]** | `git cat-file blob HEAD:lib/client.js \| sha256` | `8b3d19bb052d06d6`（16 位）|

**同一个内容会有两个不同的值** —— 报告时必须写清用的是哪种，
否则下一个人拿 sha256 去比 SHA-1，会以为对不上。
**建议两者都给**（git 对象 id 便于 `git cat-file` 复现，内容 sha256 便于和工作区比对）。

**规则**：

1. 交付说明里的 pin，**必须是 commit blob 的哈希**；若只报「工作区哈希」，
   必须同时注明「工作区可能已前进、该哈希对应某个中间状态」
2. 复核别人的绿灯，用 `git cat-file blob` 取副本跑，**不要直接测工作区**
3. 每条测试结论都要带 **「断言集版本 + 条数」**（例如 `ui-spec #1~#22 → 22/0`）。
   只说「14/14」无法判断测的是哪一版 —— 我们实际踩过：一方报 14、实际已到 16
4. 宣布「定稿」时同时给出 **commit hash + blob 哈希 + 断言条数**，让复核方能独立复现

**为什么不拿工作区哈希当判据**：本仓 `core.autocrlf = true`，一次 `checkout`/`reset`
就可能把 LF 写成 CRLF —— **内容没变，sha256 却变了**。
判断「文件是否被改」用 **git blob 哈希**；判断「行为是否变了」**重跑测试**。

> 依据：2026-09-30 实践。当时 `lib/client.js` 十分钟内被改 5 次，
> 一方报的 pin 与另一方测的工作区不是同一版本，两边都以为在说同一件事。
> 改用「commit blob + 断言集版本」后，结论才可复现。

#### 可复现性有两个轴 —— 缺一个就不可复现

| 轴 | 要求 |
|:---|:---|
| **代码轴** | 被测代码必须已提交（pin 绑 commit 的 blob）|
| **测试轴** | **测试定义本身也必须已提交** |

**只提交代码、不提交测试，等于没复现** —— 因为「189 条」这个数字是**工作区的测试文件**算出来的：
改动断言、增删用例、调整判据，都会让同一个代码 blob 得到不同结论。
所以宣布「N 条全绿」时，**代码与测试必须同一批进 commit**。

**另一个容易漏的**：报告说「全套绿」前，**先数一遍测试文件个数**。
2026-09-30 就踩过：口头说「189 条全绿」，实际 `test/` 下有 **10 个文件**，
第 10 个（宿主侧设置）当时是 `52/14` —— **漏报一个红文件比少报几条断言严重得多**。

### 8.2 测试的两个层次（静态门禁 / 运行期冒烟）

| 层次 | 文件 | 测什么 | 特点 |
|:---|:---|:---|:---|
| **静态门禁** | `test/ui-spec.test.mjs` | 规范条款（token/圆角/无障碍/浮层结构） | **零 DOM**：只读源码文本 + `vm` 求值数据表 + `import` 纯模块 |
| **运行期冒烟** | `test/client-render.test.mjs` | 真实渲染行为（缩略图门槛/URL 编码/回退/时间双形状） | 用 mock React 真跑组件；**带「hook 黄金值」校准护栏** |

**为什么两个都要**：静态门禁查不到「状态用错」，运行期冒烟查不到「规范违反」。
**互补，不重复。**

**运行期测试的专有陷阱 —— mock 队列位置错位**：
`client-render` 用**按位置喂的 states 队列**模拟 `useState`。一旦有人**增删或调换 hook**，
后面所有值静默错位，断言会变成「用错状态也能过」。
因此它带一条**校准护栏**：`hook 实际调用数 === EXPECTED_HOOK_CALLS`（**黄金值相等**，
不是 `>=` —— `>=` 只能发现 hook 被删，发现不了被插入）。
**改组件 hook 顺序的人有责任同步这个常量。**

### 8.3 写断言的纪律（实践总结）

1. **断言必须指向规范条款**。实现变了断言就成了「保护 bug」。
   需要新断言时**先补规范**（如 UI-SPEC §十一），再照钉。
2. **只钉「结构选择」，不钉「运行期质量」**。
   例如浮层：钉「存在夹取函数且被调用」「根节点 `position:fixed`」，
   **不钉**「翻转后看起来对不对」—— 后者依赖布局，硬写断言会乱咬。
3. **禁止做某事时，要指向「最可能被顺手做出来」的具体形态**，
   而不是泛泛查关键字。例：session-changes 在「从未观察到公告」时返回 404，
   测试额外断言 `!('files' in body)` —— 防的是**将来有人顺手加个兜底列表**。
4. **假警报比漏报更耗团队信任**。判据宁可窄一点，也不要让它乱咬；
   发现自己写出假警报要**主动上报**。

   **已观察到的三类假警报**（2026-09-30 一天内自曝 3 次，各属一类）：

   | 类型 | 失效模式 | 实例 | 对策 |
   |:---|:---|:---|:---|
   | **① 字面量污染** | 判据太宽，撞上无关文本 | 用裸 `opener` 判据 → 命中字符串 `"noopener"` | 判据要带结构（如「声明了 ref 且调用了 `.focus()`」）|
   | **② 邻近误伤** | 用空间距离代表语义关系 | 「±320 字符内出现 toast」→ 误报自带 `clearInterval` 的 retryTimer | 看**回调体**里做了什么，而不是附近有什么词 |
   | **③ 结构演进失效** | 实现重构后判据不再成立 | 「坐标点 ±700 字符内有夹取」→ 夹取被提成函数后，**正确实现反被报警** | 改成**语义级**：全文件存在该能力 + 调用点用的是**计算结果**（`placed.*`）|

   **⭐ 第三类可以「提前预防」，不只是事后发现（2026-09-30 实例）：**

   有一条判据原本写的是「**一律禁止** `onDragStart`」—— 它写下时**完全正确**（当时只有「拖进来 = 登记」一种拖拽语义）。
   但当晚要新增「**拖出去 = 引用**」，那个功能**正需要** `onDragStart`。
   **写测试的人在功能落地之前就预测到了这个冲突**，于是把判据从「关键词级」改成了「**语义级**」：

   | 拖拽语义 | 判据 |
   |:---|:---|
   | 拖进来 = 登记 | `onDrop` **必须存在**（配对的正向要求）|
   | 拖出去 = 引用 | **允许** `onDragStart`，**但必须真的带载荷**（`.setData(`）|
   | 框选选中 | **禁止** |

   并且做了**四向 bite**：现在的代码 → 绿；**模拟新功能 → 仍绿（关键：不误杀也要验）**；忘带载荷 → 红；加框选 → 红。

   **两条可复用的结论**：
   1. **判据要跟着「语义」走，不要跟着「关键词」走。** 同一个 `onDragStart`，在「拖出引用」里是对的、在「拖拽选中」里是错的。
      **关键词级判据会随功能演进而由对转错** —— 这就是第三类的成因，也说明它**可以被预见**。
   2. **bite 要有一向专门验「不误杀」**：构造**新功能**的样子喂进去，看判据是否仍然绿。
      多数人只验「该红时红了」（正向）和「错的样子会不会被放行」（反向），
      **唯独不验「新功能落地时会不会把门禁炸了」** —— 而那一向正是稳态的关键。

   **③ 最危险** —— 它会在别人**做对事**的时候报警，逼人为了过测试而写坏代码。
   写断言时先问一句：**「这个判据在实现被合理重构后还成立吗？」**

5. **当一条判据要反复调参数才能不误报时，问题不在参数，在判据的度量方式。**

   实证：`ui-spec` #20（浮层坐标必须有夹取）改了 **3 版**，前两版都因为用「±700 字符窗口」
   误杀正确实现 —— v1 是夹取被提成 `placeMenu()` 函数（窗口内看不到）、v2 是 `vw`/`vh`
   两行落在窗口外。**两次「修复」都是把窗口调宽，两次都再错一次。**
   v3 才换成正确做法：**追这个值的来源**（裸标识符 → 找它最近一次赋值 → 在赋值里找夹取/放置信号）。

   **判据的度量方式，按可靠性排序**：
   | 度量 | 可靠性 | 说明 |
   |:---|:---|:---|
   | **值来源追踪**（追赋值链）| 高 | 语义级，不受实现结构调整影响 |
   | **全文件能力存在性 + 调用点语义**（如「用的是 `placed.*` 计算结果」）| 中高 | 比纯距离强，但要小心下面的「输入/输出混淆」|
   | **字符距离窗口**（±N 字符内出现某关键词）| **低** | 只要实现一重构就失效；**不要用它当判据** |

6. **两种 bite-test 方向：正向验「漏」，反向验「宽」。**

   | 方向 | 做法 | 能发现 | 发现不了 |
   |:---|:---|:---|:---|
   | **正向** | 把**正确实现**改错，看断言是否变红 | 判据**过窄**（漏报）| 判据**过宽**（误放行）|
   | **反向** | 构造**「错的但像对的」实现**，看断言是否误绿 | 判据**过宽** | —— |

   **反向这一半必须专门做**，因为「读代码检查判据」查不出过宽 —— 过宽的定义就是
   「它接受了不该接受的东西」，而**不写那个东西出来，你根本不知道它接不接受**。

   **实证（2026-09-30 一天内 7 次「判据不严」，其中 6 次由反向 bite-test 发现）**：

   > **这个比例本身说明：「过宽」这类错误靠读代码是读不出来的。**
   > 所以本项目的纪律是：**每条断言写完，先构造一个「错的但像对的」实现跑一遍** —— 不是可选步骤。

   第 7 次那例最能说明问题：判据原写「**所有** `aria-selected` 都是常量才算错」，
   bite 只把「行」那一处写死成 `"false"` → **整个断言照样绿**（因为另一处仍是动态的）。
   改成「按视觉与无障碍同源**逐点**钉」之后才咬得住。**「覆盖了」和「覆盖住了」是两件事。**
   - #20 把 `anchor` 列进「放置结果」关键词表 —— 而 **`anchor` 是输入几何**（触发元素的 rect），
     `var x = anchor.left`（**原始坐标、零夹取**）被判成合规。**关键词类判据分不清「输入」与「输出」，这是它的固有盲区。**
   - #23 最初写「存在对 schema 变量的迭代」→ 正样绿；把喂给分组的 `keys` 换成**字面量数组**后
     **仍然绿**（别处**残留**的迭代满足了判据）→ 改成**两跳追踪**（先找 `KEYS` 从哪来，再验它由
     `Object.keys(schemaVar)` 产生）后才准确报红。

   **负判据要配对正向要求，否则会退化成「永远为真」**：
   实证 —— 「禁止拖拽选中」（禁 `onDragStart`/`dragSelect`）这类负判据，
   **什么都不做也算通过**。所以它配对要求了 **`onDrop` 必须存在**：
   这样「拖拽被整个删掉」时判据也会红（前提失效 → 必须回来更新），**不会变成一句空话**。

   **一条实用判据**：写断言时问自己 ——
   **「如果我是一个想偷懒的实现者，怎么用最少的改动让它变绿，而功能其实是假的？」**
   然后**真的那么改一次**。这个「假实现」就是反向 bite-test 的输入。

   另一条经验：**判据要追「值从哪来」，不要看「附近有什么词」**（见第 5 条）。
   过宽通常来自「关键词匹配」或「存在性检查」，过窄通常来自「距离窗口」。

7. **单边断言常可被「什么都不做」或「什么都不判」绕过 —— 考虑成对钉。**

   实证（`@` 来源的降级路径）：
   - 只钉「没有该服务时不抛」→ **一个从不注册的实现也能过**（功能等于没做）
   - 只钉「有该服务时注册」→ **一个不判空、不 try/catch 的实现也能过**（新宿主绿、旧宿主抛）

   → 钉成一对：**存在时恰好注册 1 次**（并断言关键字段）+ **不存在时不抛、返回 disposer、且不虚报注册**。
   **但不要钉日志文案**（文案太脆，改一个字就红）。**钉行为的两半，不钉措辞。**
7. **判据本身会被污染：校验方法要跟着一起校验。**

   今天两个人**独立踩到同一个坑** —— 说明它是一类，不是两次意外：

   | 谁 | 判据 | 命中的是 | 后果 |
   |:---|:---|:---|:---|
   | 文档侧 | 用「端点字符串是否出现」判定功能搬过来没 | **他自己写的注释**（被实现方粘进了源文件头部）| 差点报出「已完成」的反结论 |
   | 测试侧 | `indexOf('产物操作')` | **注释里的等号写法**（节点用的是冒号）| 切片窗口整体偏移 → **三条全误报** |

   **两条可复用的结论**：
   - **「文字里出现了某个符号」不等于「代码里有它」**。
     它和「字面量污染」（第一类）**同族** —— 都是把「**存在某个字符串**」当成了「**存在某个事实**」，
     只不过污染源从「不相关的代码」换成了「**自己写的文字**」。
     **而且越是一份写得详细的判定表，越容易成为污染源**。
   - **判据要和它的校验方法一起设计。** 例：「端点字符串判据」必须配「**先剥掉注释再搜**」；
     「按标签名找节点」必须配「**只认节点形态**（冒号而非等号）。

8. **脚手架的行为差异也会污染判据：要分清「测的是产品」还是「测的是脚手架」。**

   今晚实例：假 React（mock harness）**在 `h(Component, …)` 创建元素时就调用组件**，
   而真实 React **只在返回的树里渲染**。
   于是父组件在 early-return **之前**构造的子元素，在 harness 里被计入，**在真实 React 里不会** ——
   表现为「某路径 `hook 20 ≠ 槽位 19`」。

   **为什么它比「测试过期」更隐蔽**：
   - 「测试过期」是**明牌**（校准护栏一喊就知道该改哪）
   - **这个是让判据的前提与真实行为不一致，而且它不会红** ——
     因为**它测的是脚手架，不是产品**。若按 harness 的顺序写「某路径不该有 X」的断言，
     那条断言**在真实 React 下是错的**，而**它永远绿**。

   **可复用的做法**：
   - 遇到这类差异，**照脚手架的真实行为喂**，并在**注释里写明「这是脚手架行为、不是产品行为」**
     （**否则后人会按它去改产品代码**）
   - 问一句：**「这条判据红了，是产品错了，还是脚手架与产品不一样？」**
   - **脚手架的差异要同步给同源 harness 的使用者**（今晚就同步给了同源的另一套）

### 8.4 什么时候**不该**写判据

写判据的纪律在 8.3，但**「不写」也是一种判断**。
2026-09-30 夜里出现三次同型情况，每次都是「**差点写了一条会惩罚正确实现的判据**」，
而**三次的解法都不是「把判据改得更细」，而是「先不做 / 先问」**：

| # | 差点写的判据 | 会误杀的正确做法 | 正确动作 |
|:-:|:---|:---|:---|
| 1 | 一律禁止 `onDragStart` | 「拖出去 = 引用」正需要它 | **预见冲突** → 改成三语义各自钉死 |
| 2 | hover 浮出层**必须** `position:absolute` | 「固定占位 + `visibility`」同样保证行高不变 | **实现方主动公告** → 改钉不变量 |
| 3 | hover 浮出层**只认** `visibility:hidden` | 卡片那处用的是 `opacity` + 绝对定位 | **按公告预先改** → 属性级不变量 |

**还有第四种情形，与前三种不同类** —— 前三种是「会误杀正确实现」，这一种是「**会把已知缺陷固化成规范**」：

| # | 差点写的判据 | 为什么不写 |
|:-:|:---|:---|
| 4 | 「失败时必须含结构化 `reason` 字段」 | 实现当前是靠状态码**字符串包含**判的（已知脆做法）。**钉它 = 把这个脆做法固化成规范**，后人反而不敢改。正确动作：**先不写**，等宿主补上 `reason` 后，再钉一条更有意义的：「**不许用字符串包含判状态**」。 |

**这一条的普遍意义**：**判据不只会误杀对的，也会保护错的。**
当一个实现已知不够好、但「能用」时，把它写成判据，等于**给它发了一张免死牌**。
正确做法是：**把它记下来（如写进待办 / 提给对方），但不把它写进门禁。**

**四条可复用的判断**：
1. **实现没落地之前，不要按猜的形状写判据** ——
   猜结构 = 把「我以为的实现」写成了「必须的实现」。
   正确动作：**先不写**，等名字/形状，或写成「结构性版本」（只钉不变量）。
2. **实现方愿意预告结构时，去问** ——
   今晚验证三次：**「让实现方预告结构」比「猜结构」可靠得多**。
3. **判据要钉「不许发生什么」，不是「必须怎么写」** ——
   同一件事可以有多种正确实现（占位 / 绝对定位 / 未来的 grid 轨道），
   **钉实现方式会把「更好的做法」判成违规**。

**判别口诉**：写完一条判据，问自己 ——
> **「如果实现方换一种同样正确的写法，它会不会红？」**
> 会 → 这条钉的是实现，不是不变量 → **改成钉不变量，或者先别写**。

### 8.5 任何「当前状态」类主张，必须在**报告时刻**重新取

同一类问题在一晚上出现了三种形态：**前两种是「采集方法」的问题，第三种是「时序」的问题**。

| 方向 | 表现 | 方法 |
|:---|:---|:---|
| **漏报** | 数字**滞后**（少算）| **数文件个数** / **复跑**（不引用上一轮结果）|
| **假报** | 数字**会抖**（把机器负载当成缺陷）| **不写绝对时间** / 不写基于耗时的断言 |
| **引用过期** | **采集时刻 ≠ 报告时刻** —— 既没少算也没抖，**只是陈述时已经变了** | **报告前重新取** |

**为什么第三类要单列**：
- **前两类只要修好「采集方法」就结束了**（去数一下、去重跑一次）
- **第三类每次报告都可能发生**，**只能靠「报前重取」这个习惯**
- **⭐ 而且它特别容易发生在「我刚刚才看过」的地方** ——
  正因为刚看过，人就不会再看；而**中间已经变了**
  （今晚实例：几十分钟前看过 `git status`，中间有人提交了，报告时仍引用旧值）

**准确的说法**：
> **任何「当前状态」类主张（测试条数、git 跟踪状态、端口、文件是否存在、进程是否在跑），
> 必须在报告时刻重新取，不引用任何一次更早的观察。**

**它和「漏报」的区别**：漏报是「**看错了范围**」，引用过期是「**看对了，但看的是过去**」。
