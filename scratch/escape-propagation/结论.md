## Q1 · `stopPropagation()` 是否阻止**同一元素上**的其他监听器？与 `stopImmediatePropagation()` 的差别？

### 答
**不阻止。** `stopPropagation()` 只阻止事件走到**其他节点**；同一个节点上的其他监听器**照跑**。
要连同一节点上的后续监听器一起掐掉，必须用 `stopImmediatePropagation()`。

### 权威来源

**MDN · `Event.stopPropagation()`**（<https://developer.mozilla.org/en-US/docs/Web/API/Event/stopPropagation>）原文：

> The **`stopPropagation()`** method of the [`Event`](https://developer.mozilla.org/en-US/docs/Web/API/Event) interface
> prevents further propagation of the current event in the capturing and bubbling phases.
> It does not, however, prevent any default behaviors from occurring; …
> **It also does not prevent propagation to other event-handlers of the current element.
> If you want to stop those, see [`stopImmediatePropagation()`](https://developer.mozilla.org/en-US/docs/Web/API/Event/stopImmediatePropagation).**

**MDN · `Event.stopImmediatePropagation()`**（<https://developer.mozilla.org/en-US/docs/Web/API/Event/stopImmediatePropagation>）原文：

> The **`stopImmediatePropagation()`** method … **prevents other listeners of the same event from being called.**
> If several listeners are attached to the same element for the same event type, they are called in the order in
> which they were added. If `stopImmediatePropagation()` is invoked during one such call, **no remaining listeners
> will be called, either on that element or any other element.**

**WHATWG DOM Standard**（<https://dom.spec.whatwg.org/#dom-event-stoppropagation>）：

> The `stopPropagation()` method steps are to **set this's stop propagation flag**.
>
> The `stopImmediatePropagation()` method steps are to **set this's stop propagation flag and this's stop immediate propagation flag**.

规范把「拦不拦同节点后续监听器」这件事完全交给 `stop immediate propagation flag`，
而 `stopPropagation()` **不设**这个 flag —— 与 MDN 一致。

### 实测（Chrome 150）
```
Q1a 同元素3个监听器，第1个调 stopPropagation()          → 实际被调用: ["A","B","C"]
Q1b 同元素3个监听器，第1个调 stopImmediatePropagation() → 实际被调用: ["A"]
Q1c 同元素 capture 监听器调 stopPropagation()           → 实际被调用: ["capture-1"]（bubble 那个没跑）
```

⚠️ **Q1c 是个容易误读的点，必须点明**：同元素上 capture 监听器调 `stopPropagation()` 后，
同元素的 **bubble** 监听器**没有**跑。但这**不是**「拦住了兄弟监听器」——
而是因为 **capture 与 bubble 是两个不同阶段**，bubble 阶段在**另一个 path item 的 invoke 调用**里，
那一次 invoke 开头的 `stop propagation flag` 检查把它挡掉了（见 Q2/Q4 的规范引文）。
所以「同元素不拦」这条只适用于**同一阶段**内的多个监听器。

## Q2 · 同节点同阶段多个监听器的调用顺序由什么决定？capture 与 bubble 混合时呢？

### 答
- **同节点、同阶段**：由 **注册（添加）顺序**决定 —— 先 `addEventListener` 的先跑。
- **同节点、不同阶段**：**capture 恒在 bubble 之前**，与注册顺序**无关**（实测 Q2b：bubble 先注册、capture 后注册，capture 仍先跑）。
- **跨节点**：整条路径先跑一遍 capture（从外往里，tree order 的逆序），再跑一遍 bubble（从里往外）。**window 在最外层**。

### 权威来源

**MDN · `Event.stopImmediatePropagation()`** 原文（同上）：

> **If several listeners are attached to the same element for the same event type, they are called in the order in which they were added.**

**MDN · `EventTarget.addEventListener()`**（<https://developer.mozilla.org/en-US/docs/Web/API/EventTarget/addEventListener>）
`capture` 选项说明原文：

> A boolean value indicating that events of this type will be **dispatched to the registered `listener` before being
> dispatched to any `EventTarget` beneath it in the DOM tree.** If not specified, defaults to `false`.

**WHATWG DOM Standard · §2.1 Introduction to "DOM Events"**（<https://dom.spec.whatwg.org/#introduction-to-dom-events>）原文：

> Effectively, all the object's inclusive ancestor event listeners whose `capture` is true are invoked,
> **in tree order**. And then, if event's `bubbles` is true, all the object's inclusive ancestor event listeners
> whose `capture` is false are invoked, **now in reverse tree order**.

**WHATWG DOM Standard · dispatch 算法主循环**（<https://dom.spec.whatwg.org/#concept-event-dispatch>）原文：

> **For each item of event's path, in reverse order**:
> If item's shadow-adjusted target is non-null, then set event's eventPhase attribute to `AT_TARGET`.
> Otherwise, set event's eventPhase attribute to `CAPTURING_PHASE`.
> Invoke with item, event, "capturing", …
>
> **For each item of event's path**:
> If item's shadow-adjusted target is non-null, then set event's eventPhase attribute to `AT_TARGET`.
> Otherwise: If event's bubbles attribute is false, then continue.
> Set event's eventPhase attribute to `BUBBLING_PHASE`.
> Invoke with item, event, "bubbling", …

**WHATWG DOM Standard · inner invoke**（<https://dom.spec.whatwg.org/#concept-event-dispatch> 同页）原文：

> **For each listener of listeners, whose removed is false:**
> If event's type attribute value is not listener's type, then continue.
> …
> If phase is "capturing" and listener's capture is false, then continue.
> If phase is "bubbling" and listener's capture is true, then continue.
> …

即：**遍历 `event listener list` 这个有序列表**（`add an event listener` 时 append，见
<https://dom.spec.whatwg.org/#concept-event-listener>「The event listener is **appended** to target's event listener list」），
同一趟里按表内顺序 ⇒ **注册顺序**；而「哪一趟」由 phase 参数决定 ⇒ **capture 趟整体先于 bubble 趟**。

### 实测（Chrome 150）
```
Q2a 同元素 bubble 按注册顺序 reg1,reg2,reg3 → ["reg1","reg2","reg3"]
Q2b 同元素混合：bubble先注册、capture后注册   → ["capture-reg2","bubble-reg1","bubble-reg3"]
Q2c window/doc 各挂 capture+bubble            → ["window-capture","document-capture","document-bubble","window-bubble"]
```

## Q3 · 一次真实按键的捕获阶段事件路径**是否包含 window**？（window 上 capture 的监听器是否比 document 上 capture 的先跑）

### 答
**包含，且 window 在最外层。** 所以 **`window` 上 capture 的监听器比 `document` 上 capture 的监听器先跑**。

**机制**：事件路径是从 target 沿 `get the parent` 一路往上爬出来的；**`Document` 的 `get the parent` 会返回
`document` 的 relevant global object（即 `window`）**，所以 `window` 是路径的最后一站（最外层）。

### 权威来源

**WHATWG DOM Standard · `Document` 的 `get the parent`**（<https://dom.spec.whatwg.org/#interface-document>）原文：

> A **document's get the parent algorithm**, given an event, returns **null if event's type attribute value is "load"
> or document does not have a browsing context; otherwise the document's relevant global object.**

（`relevant global object` 对 `Document` 就是它的 `Window`。）

**WHATWG DOM Standard · dispatch 算法建路径**（<https://dom.spec.whatwg.org/#concept-event-dispatch>）原文：

> Let parent be the result of invoking **target's get the parent** with event.
> **While parent is non-null:** …
> If parent is a **Window object**, or parent is a node and target's root is a shadow-including inclusive ancestor of parent:
> … **Append to an event path** with event, parent, null, relatedTarget, touchTargets, and slotInClosedTree.
> … If parent is non-null, then set parent to the result of invoking **parent's get the parent** with event.

**为什么 `keydown` 满足前提**：该条只对 `type === "load"` 或无 browsing context 的 document 返回 null；
`keydown` 两者都不沾。（`keydown` 会冒泡这一点见 MDN 的
[UI Events / keydown](https://developer.mozilla.org/en-US/docs/Web/API/Element/keydown_event)：*Bubbles: Yes*。）

### 实测（Chrome 150）
```
Q3a composedPath()（在 window capture 里读）: ["#target","body","html","document","window"]
Q3b window-capture 是否先于 document-capture: ["window-capture","document-capture"]
```

**更强的证据 —— 真实按键的 `composedPath()`**（CDP `Input.dispatchKeyEvent`，`isTrusted=true`）：
```json
[{"trusted": true, "path": ["DIV","body","HTML","document","window"]}]
```
即：**真实按键（非合成）的路径末端就是 `window`**。

## Q4 · 在 window 的 capture 阶段 `stopPropagation()`，document 上的 capture 监听器还收得到吗？

### 答
**收不到。** 设了 `stop propagation flag` 之后，**后续每一个 path item 的 invoke 开头都会直接 return**，
所以 `document`（以及更里层的所有节点）的 capture 与 bubble 监听器**一个都不会跑**。

### 权威来源

**WHATWG DOM Standard · invoke 算法**（<https://dom.spec.whatwg.org/#concept-event-dispatch>）原文：

> **To invoke**, given an event path item pathItem, an event event, a string phase, …:
> Let targetItem be pathItem. …
> Set event's target to targetItem's shadow-adjusted target.
> Set event's relatedTarget to pathItem's relatedTarget.
> Set event's touch target list to pathItem's touch target list.
> **If event's stop propagation flag is set, then return.**
> Initialize event's currentTarget attribute to pathItem's invocation target.
> Let listeners be a clone of event's currentTarget attribute value's event listener list. …

关键就在 **`If event's stop propagation flag is set, then return.`** 这一行：
它在**每个 path item** 的 invoke 开头执行，而 path 的顺序是 **window（最外层）在最前**
（capture 趟 = path 逆序，path 末位是 window ⇒ 逆序后 window 第一个）。
⇒ window 那趟设了 flag，**document 那趟的 invoke 一进门就 return**。

### 实测（Chrome 150）
```
Q4a window capture 里 stopPropagation 后，实际被调用: ["window-capture"]
      （document-capture / document-bubble / window-bubble 全都没跑）
```

## F1 / F2 判定

### 背景（仓库只读核对）
- 抽屉 `DetailDrawer` 的 Escape：`document.addEventListener("keydown", onKey, true)` —— **document capture**（`lib/client.js:8779`）。
- 浮层 `MediaLightbox` 的 Escape：`document.addEventListener("keydown", onKey, true)` —— **document capture**（`lib/client.js:3683`），
  且其注释（`:3655-3682`）自称「必须靠 `stopPropagation` 把事件截住」。
- ⚠️ **两者同节点同阶段** ⇒ 按 Q2，**谁先注册谁先跑**。抽屉先挂载 ⇒ 抽屉先注册 ⇒ **抽屉先跑并 `stopPropagation`**
  ⇒ 浮层的处理器根本轮不到 ⇒ **按一次只关掉底下的抽屉，浮层还在 = 依琪报的「要按两下」**。

### 实测（真实按键，5 场景）
| 场景 | 监听布局 | 一次 Esc 后 | 判定 |
|:---|:---|:---|:---|
| **A 现状** | 抽屉 document capture（先注册）＋ 浮层 document bubble | 抽屉**已关闭**、浮层**还开着** | ❌ 复现「按两下」 |
| **B F1** | 抽屉 document capture ＋ 浮层 **window capture** + `stopPropagation()` | 抽屉**还开着**、浮层**已关闭** | ✅ 目标达成 |
| **C F2** | 抽屉 document capture（知道上层有浮层 → return，**不** stopPropagation）＋ 浮层 document bubble | 抽屉**还开着**、浮层**已关闭** | ✅ 目标达成 |
| **D F1 反面** | 抽屉 document capture ＋ 浮层 **window bubble** | 抽屉**已关闭**、浮层**还开着** | ❌ 说明**必须是 capture** |
| **E F1 + 注册顺序对调** | 抽屉 document capture（**后**注册）＋ 浮层 window capture | 抽屉**还开着**、浮层**已关闭** | ✅ F1 **不依赖注册顺序** |

原始输出全文：`cdp-run-output.txt`。

### F1：浮层改挂 `window` capture + `stopPropagation()`

**判定：✅ 可行。**

理由（三条，各自独立成立）：
1. **Q3 实测**：真实按键的路径包含 `window` 且在**最外层**，`window` capture 先于 `document` capture 跑。
2. **Q4 实测**：在 `window` capture 里 `stopPropagation()`，`document` 上的 capture 监听器**收不到** ——
   抽屉的处理器被干净地挡在门外，而浮层自己已经把 `lightbox` 关了。
3. **场景 E 实测**：把抽屉改成**后**注册，F1 依然一次成功 ⇒ **不依赖注册顺序**，不是巧合。

⚠️ **注意 F1 有一个必须做对的前提**：浮层**不能同时**还挂在 `document` capture 上。
场景 B 之所以成功，是因为浮层只挂 `window` capture。如果只是「在 document capture 之外再加一条 window capture」，
两条会**都**跑（同一次派发里 window 那条先跑并 stopPropagation 后，document 那条会被 flag 挡住 —— 其实也不会重复，
但**代码里留两条同名处理器**是明确的技术债）。正确做法是**把原监听从 document capture 挪到 window capture**，不是叠加。

⚠️ **F1 的附带效果（需要在方案里说清）**：`window` capture 是**最外层**，`stopPropagation()` 会连
**所有** document 级 Escape 处理器一起挡掉 —— 包括设置页（`client.js:6790`）、导入页（`:8327`）这些
同样挂在 document capture 的处理器。浮层开着时它们不响应，**符合「浮层是模态」的语义**，
但这是一次**全局行为变更**，比 F2 的影响面大。

### F2：给抽屉传「上层有浮层」的 prop，抽屉直接 return（不 stopPropagation）

**判定：✅ 可行（且是当前仓库已采用的做法）。**

理由：
1. **场景 C 实测**：抽屉先跑但直接 return（**不** `stopPropagation`），事件继续走到浮层，浮层关掉、抽屉留着 —— 一次成功。
2. 机制上它就是「把顺序问题变成显式状态」：不赌 `stopPropagation` 的阶段细节，直接由 React 的 `lightbox` 状态决定谁让路。
3. 仓库现状核对：`lib/client.js:4704` 传 `blockEscape: !!lightbox`，`:8774` `if (props.blockEscape) return;`，
   `:8783` 依赖数组含 `props.blockEscape`（这一条**必须**有，否则闭包会停在挂载那一刻的值，反而制造出新的「第一次没反应」）。

⚠️ **F2 的已知代价**：它需要**每一对**上下层浮层都手动接线。
现在只有「抽屉 ↔ 浮层」这一对；将来再加第三层（比如浮层之上再开一个确认框），
就得再传一个 prop，漏了就又回到「按两下」。F1 则天然对任意层数成立。

### 两条路的对比（供拍板）

| | F1 window capture | F2 blockEscape prop |
|:---|:---|:---|
| 一次 Esc 只关最上层 | ✅ 实测 | ✅ 实测 |
| 依赖注册顺序 | **不依赖**（场景 E 实测） | 不依赖 |
| 影响面 | **全局**：挡住所有 document 级 Escape | **局部**：只动抽屉一处 |
| 扩展到第 N 层浮层 | 自动成立 | 每加一层要新接一根线 |
| 可测性 | 要在真浏览器里跑事件才能验 | **能在渲染树上直接断言**（guard 测试盯 prop 即可） |
| 现有实现 | 未采用 | **已采用** |

### ⚠️ 必须指出：仓库注释里有一处**说反了**

`lib/client.js:8764-8765`（`DetailDrawer` 的注释块）原文：

> ⇒ 只把浮层"也改成 capture"或"也加 stopPropagation"**都解决不了**：
>   抽屉仍然先跑、先把自己关掉，用户还得按第二次。

`lib/client.js:4698-4699`（传 `blockEscape` 的地方）同族原文：

> ⇒ 光靠"改阶段/加 stopPropagation"解决不了：抽屉总会先跑并把自己关掉，
>   用户就得按第二次。

**这两句对 F1 不成立。** 上面场景 B 与场景 E 是**真实按键**实测：浮层挂 `window` capture 后，
抽屉的处理器**一次都没被调用**，一次 Esc 就只关掉了浮层。

那两句话成立的只有**「浮层也改成 `document` capture」**这一种情况 —— 因为那还是**同节点同阶段**，
仍按注册顺序、抽屉仍先跑。**「`document` capture」与「`window` capture」不是一回事**：
前者与抽屉同级（比的是注册顺序），后者在**外层**（比的是阶段/路径，根本不进同一次 invoke）。
这个区分正是 Q3 要查的东西，也是那句话出错的根源。

> 注：`lib/client.js:3676-3682`（`MediaLightbox` 的注释）**说的是对的** ——
> 它明确写了「两条都在 `document` 上，所以后注册的先跑不了（同阶段按注册顺序）⇒ 光靠阶段不够」。
> 出错的只有 `:8764` 与 `:4698` 那两处把结论外推成「改阶段/改成 capture 一律没用」的地方。

**这不影响 F2 是个好选择** —— F2 的「确定性 / 不依赖注册顺序巧合 / 能在渲染树上直接断言」理由依然成立。
但「F1 不可行」这个**论据是错的**，如果它被写进了方案文档或交接材料，建议改掉，
否则将来有人遇到「三层浮层、F2 接线漏了一根」时会以为没有退路。

### 两条修法的**共同**局限（与本判定无关，但必须一起说）
若焦点落在**跨文档的 `<iframe>`**（如 iframe 化的播放器）内部，`keydown` 会在**那个文档**里派发，
父窗口的监听器（无论挂 `document` 还是 `window`、capture 还是 bubble）**都收不到**。
这一点 F1、F2 与现状**完全一样**，不是 F1 的缺陷；`lib/client.js:3631-3633` 把
「挂 document 就能保证开着一定响应」当作理由，这个理由在 iframe 场景下**两边都不成立**。
本次**未实测 iframe 场景**（明确记为未验成项）。
